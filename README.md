# C910 HAD: первый target-драйвер OpenOCD

Основа API: OpenOCD commit 8da0578d7bce3e134821ccf10911182788debc32.
HAD-последовательности взяты из предоставленного c910_had.c/.h;
HSR.PM=2 означает Debug по предоставленной документации.

## Что готово

- Общий слой newchip_had.c/.h: IR/DR, HAD bank 0, HSR, halt с ожиданием, PC.
- Старые команды newchip_xfer и newchip id/status/halt/pc.
- Тип target c910_had: init, examine, poll, halt, вывод состояния.
- Номер ядра задаётся штатным -coreid 0..3. TAP общий для ядер.
- halt сохраняет остальные биты HCR, ждёт HSR.PM=2, обновляет target->state
  и отправляет TARGET_EVENT_HALTED. Повторный halt не дублирует событие.
- При внешней остановке poll фиксирует переход и отправляет событие.
- Причина внешней остановки пока UNKNOWN/UNDEFINED: occurrence-биты HSR
  могут быть историческими, их полноценный разбор ещё не реализован.
- Запись PC через newchip pc проверяет остановку и значение после записи.
  newchip_xfer остаётся прямым низкоуровневым доступом без этих ограничений.

Нет resume, step, reset, памяти, breakpoint/watchpoint и регистров для GDB.
resume/step возвращают ERROR_NOT_IMPLEMENTED. GDB для этого этапа отключён;
драйвер не предоставляет get_gdb_reg_list, поэтому OpenOCD его исключает
из GDB services. Не подключайте GDB и не объединяйте ядра в SMP пока.
PM=3 (Reset/Idle) отображается как UNKNOWN: это не доказательство reset.
PM=1 (LowPower) отображается как RUNNING: ядро не в debug-halt.

## Установка

Распакуйте архив рядом с исходниками OpenOCD. Остановите запущенный OpenOCD.
Сначала посмотрите изменения (путь замените своим):

```sh
python3 c910-had-stage1/apply_to_tree.py /path/to/openocd --dry-run
python3 c910-had-stage1/apply_to_tree.py /path/to/openocd
```

Скрипт обновляет только перечисленные файлы. Существующие файлы сохраняются
в openocd/c910-backup-ДАТА/. NEW_FILES.txt перечисляет вновь созданные файлы.
Повторный запуск не добавляет повторных регистраций. Скрипт рассчитан на
исходную структуру OpenOCD и ранее обсуждённую регистрацию newchip.
Ваш src/target/newchip/newchip.c заменяется версией из архива.

Точки подключения:

1. src/target/Makefile.am: подключение библиотеки и её Makefile.am.
2. src/target/target_type.h: extern struct target_type c910_had_target.
3. src/target/target.c: &c910_had_target в массиве target_types[].
4. src/openocd.c: newchip.h и newchip_register_commands в command_registrants[].

Это можно сделать вручную вместо скрипта. Не дублируйте уже имеющиеся записи.

## Пересборка

Из корня ваших исходников OpenOCD (с прежним окружением зависимостей):

```sh
./bootstrap
cd build
./config.status --recheck
./config.status
make -j"$(nproc)"
cd ..
```

config.status использует параметры вашего предыдущего успешного configure.
Если build/config.status нет, сначала выполните прежнюю успешную команду
configure с вашими путями к зависимостям. sudo не требуется.

## Запуск и проверка

Сначала запустите симуляцию с remote_bitbang на localhost:4445.

```sh
./build/src/openocd -s ./tcl -f jtag_scripts/c910_sim_target.cfg
```

Это самостоятельный конфиг: не добавляйте одновременно старый c910_sim.cfg.
По умолчанию создаётся одно ядро, c910.core0. Второе включается отдельной
закомментированной строкой, только если оно существует в модели.

Конфиг сохраняет проверку IR capture. Ранее наблюдавшееся сообщение
IR capture error (0 вместо 1) этим драйвером НЕ исправляется. Если ваш
рабочий конфиг уже имеет согласованные параметры TAP, перенесите их
в строку jtag newtap; не считайте отключение проверки исправлением модели.

Подключитесь telnet к порту 4444. Выполните:

```tcl
targets
newchip id riscv.cpu 0
c910.core0 arp_poll
targets c910.core0
halt 30000
targets
newchip status riscv.cpu 0
newchip pc riscv.cpu 0
```

Ожидаем ID=0x080d2b43, после halt состояние halted и HSR.PM=2.
В ваших прошлых тестах HSR был 0x000cb102; остальные биты могут отличаться.
PC может быть нулевым, если исполняемая программа ещё не загружена.

Конфиг вызывает poll off, потому что сканы симулятора медленные.
Для явного обновления используйте c910.core0 arp_poll. Для фонового опроса
можно включить poll on. targets показывает кэшированное состояние.
Старые newchip-команды обновляют железо напрямую, не target->state;
после них выполните arp_poll, чтобы синхронизировать состояние и события.

Для второго ядра после добавления target:

```tcl
targets c910.core1
halt 30000
newchip status riscv.cpu 1
```

## Ограничения ожидания

HAD halt ждёт до 30 секунд после выставления запроса. Проверка времени
происходит между JTAG-чтениями; она не прерывает блокирующее ожидание ответа
remote_bitbang. keep_alive вызывается между чтениями. Если один скан занимает
более секунды, предупреждение keep_alive всё ещё возможно.
Драйвер использует синхронный halt на первом этапе; фоновый poll не создаёт
отдельного потока, и другие команды сервера ждут завершения текущей.
